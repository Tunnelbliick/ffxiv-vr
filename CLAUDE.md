## Conventions

No comments. Don't write them in any file you touch. The one exception: `# Safety` doc comments stay even on functions that aren't `unsafe fn` - see the native DLL section below.

## Structure

The `FFXIVClientStructs` and `Dalamud` folders contain the sources for the dependencies (vendored checkouts, not this project's own code).

## What this is

A Dalamud plugin (`FfxivVr`, C#/.NET) that adds VR (OpenXR) support to FFXIV, plus a native Rust DLL (`FfxivVrNative`) that hooks the game's D3D11 device-context calls to rewrite the camera/decal/UI/light constant buffers the game writes with per-eye view/projection data, and to give the right eye its own copy of every frame-to-frame history resource. `FfxivVr.csproj` builds the Rust DLL and compiles the HLSL shaders as part of its own build, so a normal `dotnet build` produces everything needed.

There are two implementations of stereo rendering, selected via the `IRenderStrategy` interface: `SinglePassRenderStrategy` (the game's camera sits at the center of the two eyes; it drives two full render passes - left eye, then right - arming `FfxivVrNative`'s constant-buffer rewriting around each so both are reprojected from the center camera to that eye) and `AltEyeRenderStrategy` (doesn't depend on the native DLL).

## Build

- C# (`ffxiv-vr.sln`): `dotnet build --configuration Release`
- Rust (`FfxivVrNative/`): `cargo build --release`

`dotnet build` on `FfxivVr` also runs `cargo build --release` for `FfxivVrNative` and recompiles the HLSL shaders, so a plain C# build picks up changes to either.

## Architecture

### C# plugin (`FfxivVr/`)

- `Plugin.cs` is the Dalamud entry point. It builds a DI container via `AppFactory.CreateSession()` (`Microsoft.Extensions.Hosting`) and initializes the render pipeline injector, game hooks, command handling, game events, and the debug/config UI from it.
- VR on/off is driven by `VRStartStop` → `VRLifecycle` → `VRSession`, which owns the active `IRenderStrategy` (see above). When the active OpenXR runtime is SteamVR and SteamVR isn't running, `VRStartStop` has `SteamVRLauncher` start it (`vrstartup.exe` next to the runtime json, else the Steam app link) and turns VR on once `vrserver` and `vrcompositor` have been running for a few seconds, instead of letting OpenXR start SteamVR mid-session; start-at-boot skips this. `/vr resetview` and the bindable `ResetView` controller action recenter the headset (which also resets `BodyYaw`) and turn the game camera to look where the character faces (`GameModifier.ResetCameraDirection`), for when the camera was knocked off the character's heading. `ControllerPointer` (the Controller pointer setting, on by default) lets either controller act as a mouse on the UI panel in `InputManager`: pointing at the panel moves the cursor there, but only when the pointed spot moves, so a resting controller doesn't take the mouse over. A trigger or grip pressed while pointing at the panel left- or right-clicks instead of reaching the gamepad. That choice is made when the button goes down, so a cross-hotbar trigger already held never turns into a click.
- `RenderPipelineInjector` locates and patches into the game's own render command queue via signature scanning (`ISigScanner`), independent of the D3D11-hook-based constant-buffer rewriting in `FfxivVrNative`.
- `game/` holds game-state/hook glue (`GameHooks`, `GameTextures`, `GameEvents`, extended FFXIVClientStructs structs); `vr/` holds the OpenXR session/swapchain/camera/input code (including `CameraShake`: the game shakes the camera in two places the VR camera modes otherwise drop: the scene camera's look-at point, and the view matrix it builds from the camera position and look-at point (VFX camera-quake effectors such as stomp mods offset and tilt that matrix). `VRSession.UpdateCamera` high-passes the look-at offset from the character's head, plus how far the freshly built view matrix's eye, pitch and yaw stray from the camera position and look-at point and the matrix's roll, before the plugin overwrites the matrix. A matrix equal to the one `VRCamera` last wrote is skipped (the game doesn't rebuild it every frame), since reading back the plugin's own view would feed the head's roll and the applied shake into the filter and, at high strengths, latch a tilt. A non-finite input, such as the degenerate view the game builds when walls push its camera into the head indoors, zeroes the shake and resets the filter, since a latched NaN would black out the world. `VRCamera.ComputeGameViewMatrix` adds the matrix offset and angles back in every mode, scaled by the Camera shake setting (0 to 10x, with the scaled result capped at 2 yalms and 30 degrees; the debug window's test buttons fake a short stomp from one source at a time - the look-at point, the matrix's eye position, its pitch and yaw, its roll, or all matrix parts as a VFX quake - by perturbing the look-at point and view matrix `CameraShake` reads (`ShakeTest`, which turns the view with a look-at shake the way the game's rebuild would), so each runs through the same capture and filtering as a real shake from that source). Each camera mode's `ShakeOffsetAxes` says which parts of the look-at offset it adds: all of it in first person, only the height in the level and floor-locked third-person cameras, whose level view would otherwise drop vertical shake, and none in the free orbit camera, which already pitches with the look-at point. Battle effect VFX of other players, stomp quakes included, only play when the game's Battle Effects setting for them allows it); `math/` holds skeleton/IK/camera math; `config/`/`debug/` are the settings and debug (ImGui) windows.
- `sync/` is pose sync: VR players share head/arm/finger rotations through a UDP relay so other plugin users (VR or not) see them on their characters. Tracking (local motion controls and the shared pose) maps the headset space onto the character with one yaw: in first person the camera's, in third person (`ThirdPersonMotionTracking`, on by default; the shared pose is captured in third person regardless) the character's facing minus `BodyYaw`, the body heading in headset space (it follows the head beyond 45 degrees and drifts after it, or stays at the recenter forward with `SeatedPlay`), so your hands stay relative to your body rather than the camera. When `PoseSync.WantsLocalPose` says a send is due (30 Hz), `VRSession.UpdateVisibility` gets the pose from `GameModifier.CaptureSyncPose` and hands it to `PoseSync.PublishLocalPose`. With body lean on (the default, and not with body tracking), `CaptureSyncPose` saves the local transforms of the spine, neck, shoulders and arms. It runs `BodySolver`, which spreads a lean over the three spine bones so the head moves to where the headset is (`math/BodyIK.cs` holds the pure math: the headset's position relative to the recenter point, minus what turning the head alone moves the eyes, clamped, with the height ignored under `SeatedPlay`), twists the chest a share of the head's yaw, then straightens or bends the spine so the chest faces no more than 45 degrees below or 50 degrees above where the head looks (a VRIK-style chest clamp, so looking up at someone taller doesn't hunch the torso), and raises or pushes the shoulders toward far or high hands. The neck takes its share of the head's turn relative to the chest, here and when a received pose is applied, so it always sits between the chest and the head. It then re-runs the arm IK from the moved shoulders, captures with `SyncRegions.Spine` and restores the saved transforms, so the local camera and body are unchanged and only the shared pose leans; `GameHooks`' `RenderSkeletonList` detour calls `PoseSync.Update` every frame, VR or not, to keep the relay connection alive and apply received poses. Only rotations are sent and written (model-space bone rotations from the fixed `SyncBones` table, plus the head as a rotation relative to the character's facing), never translation or scale, so character scale on either side can't break it; `math/SyncSkeletonModifier.cs` captures and applies them, `RemotePose` smooths and fades them, and `SyncProtocol` holds the packet format (the relay's keepalive reply, `Welcome`, also carries how many other clients share the room, read as optional so a 12-byte reply from an older relay still works), quaternion packing and hashed room/player ids. The table already includes the waist and legs (`SyncRegions.Legs`) for when a full-body tracking source exists.
- `FfxivVrRelay/` is the standalone relay server (.NET console app, Dockerfile, deploy notes in its README); its packet constants must match `SyncProtocol` (`Tests/RelayTest.cs` checks).
- `FfxivVr/native/FfxivVrNative.cs` is the C# side of the FFI boundary to the Rust DLL: it loads `ffxiv_vr_native.dll` via `NativeLibrary` and exposes each `ffxiv_vr_native_*` export as a typed delegate.

### Native Rust DLL (`FfxivVrNative/`)

Builds as a `cdylib` (`ffxiv_vr_native.dll`). It vtable-hooks the game's `ID3D11DeviceContext` methods (via `retour`) - `OMSetRenderTargets`, `Map`, `Unmap`, `UpdateSubresource` for the camera buffers, `DrawIndexedInstanced` for the footprint instance buffers, plus every view-binding/clear/copy call for per-eye history resources - to track which render pass (geometry/compositing) is currently bound and rewrite the camera/decal/UI/light constant buffers the game writes during that pass with the active eye's view/projection data, so each of the two render passes draws from its own eye's VR camera instead of the center camera the game set up. All mutable state lives in one `AppState` behind a global `Mutex` (`lib.rs`), driven entirely through the hook trampolines in `hooks/` and the `ffxiv_vr_native_*` `extern "system"` FFI exports in `lib.rs`.

`unsafe` should only appear where code genuinely interacts with third-party/FFI surface: `windows`-crate COM method calls, `retour::GenericDetour` install/call, and raw pointers crossing the FFI boundary (the `ffxiv_vr_native_*` exports, the `declare_hook!`-generated `detour`/`original` functions in `hooks/`, `AppState::new`, `hooks::vtable_entry`, `hooks::buffer_updates::try_modify_camera_buffer`). A function should be a plain `fn`, not `unsafe fn`, just because it calls something else that's internally unsafe — mark it `unsafe fn` only if it itself takes a raw, untyped pointer with a precondition the type system can't express. Keep the `unsafe { ... }` block as small as possible (wrapping just the actual COM/FFI call), and keep any `# Safety` doc comment even after dropping `unsafe fn` from a function's signature — it still documents a real invariant, just one already guaranteed by construction (e.g. a raw pointer argument only ever being live for the duration of the hook call that produced it) rather than one each caller needs to separately prove.

This crate started as a Rust port of a former C# `FfxivVr/vr/SinglePassRenderStrategy/` folder; that C# folder no longer exists (fully replaced), and the code no longer documents itself by reference to it - see Conventions above.

Key modules:

- `lib.rs` — owns the global `AppState` behind a `Mutex`, defines every `ffxiv_vr_native_*` FFI export (`init`/`shutdown`/`set_config`/`set_projection_matrix`/`set_manual_second_pass_active`/`on_frame_end`/...), and sets up the file logger.
- `hooks/` — `mod.rs` installs and uninstalls every hook (`install_all`/`uninstall_all`) and holds the shared `run_hook` helper plus the eye-resource helpers every group uses (`eye_view(s)`/`eye_resource`, which record each access and swap to the right eye's mirror; `with_eye_view(s)`; and `sync_bound_views`, called from `lib.rs` at each eye switch). It also defines `declare_hook!(name, vtable_index, fn(context, args...) { body })`, which gives each hook its own module containing `Fn`, `DETOUR`, `INDEX`, the `extern "system"` `detour` (the body), and `original(...)`, which calls the unhooked method. The hooks are grouped by job, and each group file holds that hook's logic alongside it: `render_targets.rs` (tracks which render pass - `Pass::Geometry`/`Pass::Compositing` - is bound from `OMSetRenderTargets`), `buffer_updates.rs` (Map/Unmap/UpdateSubresource: shadows write-mapped constant buffers so they can be inspected and rewritten before reaching the GPU, and `try_modify_camera_buffer` dispatches to `modifiers` to rewrite the active eye's camera/decal/UI/light buffers), `draws.rs` (footprint correction, and binding the nameplate billboard shader - see `billboards.rs`), `shader_resources.rs`, `clears.rs` and `copies.rs`. Each group is re-exported so callers use `hooks::<name>::original`.
- `eye_resources.rs` — per-eye copies of history resources. The game replays the same command list for both eyes, so ping-pong/history textures (AO, glare, prev depth, volume shadow) would otherwise carry one eye's output into the other. Every bind/clear/copy during an eye pass is recorded as a read or write; a resource that is written in an eye pass and also read before being written in some pass gets a same-desc mirror (2D textures only, excluding the geometry/composition textures and tiny textures). While the right eye is active, every render-target/depth/UAV/SRV bind, clear, and copy is swapped to the mirror, and `hooks::sync_bound_views` re-swaps whatever is already bound at each eye switch.
- `camera_state.rs` — `CameraState`, the per-eye view/projection overrides set over FFI, the active eye, and the game's original center projection and view (captured by `modify_camera_parameters`); every `modify_...` function reads it to compute the active eye's projection.
- `shadow_buffers.rs` — `ShadowBuffers`, the CPU-side copies that write-mapped camera buffers are redirected to between `Map` and `Unmap`, plus a cache of each buffer's byte width.
- `billboards.rs` — `Billboards`, a geometry shader (`FfxivVr/shaders/BillboardShader.hlsl`, compiled to `.cso` with the other shaders and embedded in the DLL with `include_bytes!`) and its constant buffer. Its `MAX_ANCHORS` is defined in both the HLSL and Rust (a Rust test checks they agree); `Tests/NameplateAnchorLimitTest.cs` asserts `NamePlateNumberArray.ObjectData` still has that many slots. `hooks::draws` binds it around every quad-list `DrawIndexed` (40-byte vertices, a multiple of 6 indices) in the compositing pass whose VS constant buffer 0 holds a screen projection (nameplate quads), turning each quad to face the eye, spinning it so its up matches world up (taken from the game's view matrix, captured by `modify_camera_parameters`) and scaling it back to its on-axis size. The pivot is the nearest nameplate anchor in the quad's depth plane, so a plate's icon and text move as one piece; each anchor pairs a nameplate's UI-space `X`/`Y`/`Depth` (which matches quads to their plate) with its world-space `GetNamePlateWorldPosition` (taken into the eye's view space with the game's view matrix), and the shader moves the plate from the former to the latter (scaled to keep its on-screen size, kept at least `MinPivotDistance` from the eye, and left at the anchor if the latter is behind the eye) before turning it, since the game pulls its own position toward the game camera; the constants are only re-uploaded when the eye's inputs or the anchors change; anchors are collected by `NameplateModifier` and passed over `ffxiv_vr_native_set_nameplate_anchors` before each frame's eye passes.
- `math.rs` — `Vec4`/`Mat4` with `mul`/`invert`/`transpose`, used for all camera-matrix math.
- `modifiers/` — per-constant-buffer camera modifiers, one file per buffer type (named after the type, holding it and its `modify_...` function): `camera_parameters` (the game's main view/projection buffer), `vs_view_projection_matrix`/`ps_view_projection_inverse_matrix` (the decal shaders' `g_VS_ViewProjectionMatrix`/`g_PS_ViewProjectionInverseMatrix`), `clip_to_world_matrix` (the fog shader's row-major `cC2W` inverse view-projection), `projection_matrix` (screen-space UI element projection), `light_param` (per-light world-view-projection), `world_view_proj_matrix` (a per-draw row-major world-view-projection such as the weather-particle shaders' `g_WorldViewProjMatrix`), `sky_quad_param` (the moon's screen-space quad), `footprint_instances` (the footprint decals' per-instance vertex buffer, matched by its fixed 28800-byte size, holding each footprint's row-major world-view-projection and its inverse; the game cycles through several of these, filling each one outside the eye passes and drawing it the following frame, so the `DrawIndexedInstanced` hook (`hooks::draws::correct_bound_footprints`) re-uploads an eye-corrected copy of whichever one is bound, once per eye), `sun_modifier` (`SunModifier`, which reprojects the sun's screen-space `cSunParam`, adding the eye's roll - the angle of world up in the eye's view, since the game camera already carries the headset's roll - to the starburst rays' angle offset so they stay fixed to the sky, and remembers the game's original sun position for the active eye so it can recognize and reproject the god-ray `cRadialBlurParam` and lens-flare `cLensFlareParam` positioned from it); `mod.rs` holds the shared `Pass` enum.

### Shaders (`FfxivVr/shaders/`)

`VertexShader.hlsl`/`PixelShader.hlsl` are the VR compositor's own shaders (drawing the final quad to the HMD), and `BillboardShader.hlsl` is `FfxivVrNative`'s nameplate geometry shader. `CompileShaders.ps1`/`CompileShaders.sh` compile all three to `.cso`; the first two get embedded as resources in `FfxivVr.csproj`, and the last is pulled into the Rust DLL with `include_bytes!`, so `CompileShaders` runs before `cargo build` and a standalone `cargo build` needs a prior `dotnet build`.
